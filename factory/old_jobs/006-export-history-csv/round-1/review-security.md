## Verified

**The export is local; no secrets, network, server or telemetry.** The only new data paths are the web Blob download (`History.jsx:64-65`) and the Capacitor Filesystem + Share call (`mobile.js:139-143`, already shipped and unchanged in behaviour). Nothing added in the diff calls `fetch`/`XMLHttpRequest`/`sendBeacon`, opens a socket, logs data, or contains a credential. `package.json` and the lockfile are untouched (zero-line diff), so the dependency set is unchanged and Blob/URL are platform APIs.

**CSV injection guard.** `csv.js:33-41` prefixes a literal apostrophe to a non-numeric, non-boolean cell whose `String()` starts with `=`, `+`, `-`, `@`, tab or CR; numbers and booleans are exempt (`csv.js:36-38`). It runs inside `cellText`, i.e. before `quoteCell` quotes and doubles (`csv.js:43-45,55-58`), and is applied by the single writer, so every text column — notes, names, the raw-id `exercise` fallback, `date`, `unit` — goes through it. Numeric columns can only emit finite numbers (`history-csv.js:95-101`), so a malicious string in `r`/`w`/`sec`/`rir`/`rpe` is dropped rather than written. The tests pin each trigger, the numeric/boolean exemption, guard-then-quote, the deep-equal no-mutation snapshot, and a parse round-trip (`csv.test.js:33-58`). I independently probed `=SUM(A1)`, `+1`, `-1`, `@cmd`, tab, CR, a boxed `new String('=boxed')`, and an object with a throwing/returning `toString`: all guarded or quoted as intended. No bypass found.

**Quoting, CRLF and BOM are correct.** Quote iff the final text contains `,`, `"`, CR or LF, with embedded quotes doubled; CRLF between records and one trailing CRLF; BOM only with `bom: true`, and `toCSV([])` is `''` even with `bom` (`csv.js:43-58`; pinned at `csv.test.js:5-21`). The screen passes `{ bom: true }` and the mobile build writes UTF-8, so the real file begins with EF BB BF as build.md reports; the exported capture shows the success snackbar.

**Input robustness.** `historyRows` returns the header for a non-array log and skips non-object workouts, entries and sets instead of throwing (`history-csv.js:70-108`; tests `history-csv.test.js:30-46,153-158`). Malformed/absent epoch or string dates become blank (`history-csv.js:26-44`), and absent `entry.target` reads as `{}` while `isBw({ ...target, id })` still detects catalogue bodyweight (`history-csv.js:78,99`). I probed a 2 MB note, comma/quote/newline notes, `entry.id` of `__proto__`, `constructor`, an object and a number, NaN/Infinity/absent numeric fields, and `null`/`1`/`'x'`/`[]`/symbol/function inputs: no throw, no row corruption, and the note fields round-trip through `parseCSV`.

**No prototype pollution and no path/filename injection.** The only `EXIDX` access is a read (`history-csv.js:79`); `__proto__`/`constructor` lookups yield non-exercise values and `?.n` falls back to the raw id, and `{ ...target }` copies own data properties into a fresh object that is only read by `isBw` — `Object.prototype` was still clean after the probe. The filename is `opengym-history-<todayISO>.csv` from `format.js:todayISO()` (digits and dashes only), and `shareExport` writes it under `Directory.Cache` (`mobile.js:141`); no state/user string reaches a path.

**Data safety.** The export only reads `S.workouts`, `S.unit` and `entry.target` (`History.jsx:57`; `history-csv.js:73-104`). There is no store write, no persisted-shape or JSON-backup change, no `localStorage`/state write anywhere in the product diff, and no `S.active`/profile data in the file. `historyRows` sorts a fresh copy and `toCSV` only reads cells, with deep-equal snapshots pinning both (`history-csv.test.js:166-175`, `csv.test.js:52-58`). The export is additive, so no data-loss path.

**Failure handling.** On web a thrown `Blob`/`URL` error toasts `Could not export the history` (`History.jsx:63-67`); on mobile a rejection is caught with no error toast and no unhandled rejection (`History.jsx:59-61`, asserted at `History.export.test.jsx:93-99`). A dismissed share sheet is silent as the spec requires; nothing is written outside the app's private Cache, so there is no unsafe fallback.

**SECURITY.md posture.** No new network or at-rest surface is introduced: the CSV is a user-initiated, device-local copy of data the document already describes as unencrypted (`SECURITY.md:9-16`). The missing CSV mention is noted below as a documentation follow-up, not a new exposure.

## Non-blocking notes

1. **SECURITY.md does not mention the CSV.** `SECURITY.md:13-16` says "Exported backups are plain JSON" and covers the JSON backup + Android Documents copy; the new History CSV is also an unencrypted full-log export. This is a doc gap, not a blocker (the unencrypted-at-rest bullet already sets the expectation). Correction when convenient: extend that bullet to "the JSON backup and the History CSV (`Export history as CSV`)".
2. **The mobile catch is broader than "dismissed".** `History.jsx:60` swallows every rejection, so a genuine Filesystem/Share failure looks exactly like a user cancel with no feedback. The spec pins this behaviour and it mirrors `Settings.jsx:111`; it leaks nothing and leaves no unsafe state. Non-blocking, only worth a follow-up if native failures ever need surfacing.
3. **CSV construction sits outside the web try.** `History.jsx:57-58` build `csv`/`name` before the `try`, so an unexpected throw there would be an unhandled rejection with no toast. Not reachable from JSON-sourced store data (all helpers coerce, probed), but moving those two lines inside the `try` would make the handler uniformly fail-safe.
4. **Leading LF is quoted, not apostrophe-guarded.** `csv.js:33` covers `\r` but not `\n`; a cell starting with LF is quoted instead (probed, `"\n=cmd"`). Excel does not evaluate a formula after a line break, and the spec lists CR only, so this is not a bypass — optional hardening only.
5. **No end-to-end formula test.** `csv.test.js:33-50` pins the guard at the writer, but no `historyRows`/screen test injects a formula-looking note; the screen test uses benign notes. Not a defect (all cells pass through `toCSV`), but one `=SUM(A1)` note in `History.export.test.jsx` would pin the full path.

I could not exercise the real Capacitor share sheet on a device from this review; the native path is verified through the mocked screen test, the code path, and build.md's evidence. Every security-relevant claim I could re-run held.
